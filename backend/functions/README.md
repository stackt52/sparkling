# Sparkling API — Firebase Cloud Functions (`backend/functions`)

Single Express app exported as the 2nd-gen HTTPS function **`api`** (region `europe-west1`), mounted at `/v1`.
Implements [`docs/API.md`](../../docs/API.md) on top of the Supabase schema in [`backend/supabase`](../supabase).

```
Node 22 · TypeScript · express · firebase-functions v6 · firebase-admin · @supabase/supabase-js v2 · zod · pino · csv-stringify · vitest
```

## Layout

| Path | Purpose |
|---|---|
| `src/index.ts` | `onRequest` function `api` (secrets bound, region, concurrency) |
| `src/app.ts` | Express wiring: CORS → correlation → JSON → auth → idempotency → routers → error envelope |
| `src/config.ts` | `defineString` params (`SUPABASE_URL`, `API_VERSION`, `WHATSAPP_PROVIDER`, `TWILIO_MESSAGING_SERVICE_SID`, `TWILIO_WHATSAPP_FROM`, `PUBLIC_API_BASE_URL`) and `defineSecret`s (`SUPABASE_SERVICE_ROLE_KEY`, `PAYMENT_WEBHOOK_SECRET`, `TWILIO_ACCOUNT_SID`, `TWILIO_AUTH_TOKEN`) |
| `src/middleware/` | `auth` (Firebase ID token → `profiles` row → role/outlet/ownership guards), `idempotency` (API-003), `correlation` (API-010, pino), `errors` (API-004 envelope), `rateLimit` (SEC-011 token bucket) |
| `src/domain/stateMachines.ts` | Pure `canTransition*` tables for booking / quotation / work-order-task / payment |
| `src/services/` | `pricing`, `availability`, `bookings`, `quotations`, `vehicles`, `workflow` (check-in, auto-assign, steps, transitions, verify side effects), `payments` (provider adapter + idempotent webhook), `loyalty`, `gamification`, `inventory`, `notifications`, `audit`, `flags`, `admin` (KPIs, exceptions, activity, CSV exports, payments list, report summary), `integrations` (status cards) |
| `src/routes/` | One router per API.md section |
| `src/lib/` | `supabase` (service-role client, `unwrap`), `firebase` (Auth/FCM singletons), `fcm`, `whatsapp` (Twilio adapter via `fetch` + sandbox/noop adapters, E.164 normalisation), `twilioSignature` (X-Twilio-Signature HMAC-SHA1), `otp` (collection OTP + visibility rules), `pdf417` (SA licence-disc parser), `refs` (receipt numbers via RPC with max+1 fallback, reward codes, cursors), `validate` (zod helpers) |
| `openapi.yaml` | Generated by `node scripts/gen-openapi.cjs` (API-012) |
| `tests/` | vitest suites with an in-memory Supabase stub (`tests/helpers/fakeSupabase.ts`) — no network |

### Emulators

1. Copy `.env.example` to `.env.local` (params) and create `.secret.local` with the secrets — both files are git-ignored:
   ```
   SUPABASE_SERVICE_ROLE_KEY=eyJ...      # Supabase → Project Settings → API → service_role
   PAYMENT_WEBHOOK_SECRET=sandbox-dev-secret
   TWILIO_ACCOUNT_SID=AC...              # Twilio console → Account info
   TWILIO_AUTH_TOKEN=...
   ```
2. From the repo root: `firebase emulators:start --only functions,auth,storage` (ports 5001 / 9099 / 9199, UI on 4000).
3. Base URL: `http://127.0.0.1:5001/sparkling-4e89d/europe-west1/api/v1` — `GET /health` needs no token.

The emulator talks to the **real** Supabase project named by `SUPABASE_URL`; run `backend/supabase/apply.sh` first to load the schema and demo seed.

## Environment variables

Every variable the API reads, where it comes from and what happens when it is missing. Params and secrets are declared in `src/config.ts` with `firebase-functions/params`; a plain `process.env` value of the same name always wins (that is how the emulator, tests and `.env` files feed them). Values are read at request time, never at import, so the deploy-time code analysis never touches Secret Manager.

### Secrets — Cloud Secret Manager, set once per project, never in the repo (INT-006, SEC-005)

| Name | Required | Used for | Where to get it |
|---|---|---|---|
| `SUPABASE_SERVICE_ROLE_KEY` | yes | Service-role Supabase client for every database read/write (bypasses RLS; server only) | Supabase → Project Settings → API Keys → *secret* (`sb_secret_…`) or legacy `service_role` JWT |
| `PAYMENT_WEBHOOK_SECRET` | yes | HMAC key that signs/validates payment-provider webhooks (`POST /v1/payments/webhook`, sandbox confirm) | Any long random string, e.g. `openssl rand -hex 32`; a real provider gives you its signing secret |
| `TWILIO_ACCOUNT_SID` | for WhatsApp | Basic-auth user for the Twilio REST API; also used to validate `X-Twilio-Signature` | Twilio Console → Account Info (`AC…`, 34 chars) |
| `TWILIO_AUTH_TOKEN` | for WhatsApp | Basic-auth password for Twilio; HMAC key for status-callback signature validation | Twilio Console → Account Info → Auth Token |

```bash
firebase functions:secrets:set SUPABASE_SERVICE_ROLE_KEY --project sparkling-4e89d
openssl rand -hex 32 | firebase functions:secrets:set PAYMENT_WEBHOOK_SECRET --project sparkling-4e89d --data-file=-
firebase functions:secrets:set TWILIO_ACCOUNT_SID --project sparkling-4e89d
firebase functions:secrets:set TWILIO_AUTH_TOKEN  --project sparkling-4e89d
```
Secret Manager rejects empty values, and `firebase deploy` prompts for any secret that has no version yet — set them all **before** the first deploy. Missing Twilio secrets are not fatal: WhatsApp silently falls back to the sandbox adapter (see `WHATSAPP_PROVIDER`). For the emulator put the same names in `backend/functions/.secret.local` (git-ignored).

### Params — plain configuration in `backend/functions/.env` (committed defaults are fine; override per environment)

| Name | Default | Used for |
|---|---|---|
| `SUPABASE_URL` | `https://uicqczgpiqkczwyssdft.supabase.co` | Supabase project URL for the service-role client and the integrations health card |
| `API_VERSION` | `1.0.0` | Reported by `GET /v1/health` and stamped on every log line (`version`) |
| `WHATSAPP_PROVIDER` | empty → auto | `twilio` sends real messages; `sandbox` logs only and marks rows sent with a fake reference. Empty picks `twilio` when both Twilio secrets exist, else `sandbox` |
| `TWILIO_MESSAGING_SERVICE_SID` | `MG4d8b6037dc3b183f43b2622307271660` (carried over from the legacy admin) | Twilio Messaging Service that owns the WhatsApp sender; Twilio Console → Messaging → Services |
| `TWILIO_WHATSAPP_FROM` | empty | Optional direct sender `whatsapp:+27…`; only used when no Messaging Service SID is set |
| `PUBLIC_API_BASE_URL` | empty → no callbacks | Public URL of this function **without** `/v1` (printed by `firebase deploy` / `firebase functions:list`). Builds the Twilio status-callback URL `<base>/v1/notifications/twilio/status` and validates callback signatures. Empty means messages still send but delivery receipts are not collected |

Independent of these params, the `whatsapp_enabled` feature flag (table `feature_flags`, toggled in Admin → Settings) gates whether any WhatsApp message is attempted at all; it ships **off**.

### Runtime variables — set by the platform or the shell, not by you

| Name | Set by | Effect |
|---|---|---|
| `GCLOUD_PROJECT` / `GOOGLE_CLOUD_PROJECT` | Cloud Functions runtime / emulator | Firebase Admin project id; falls back to `sparkling-4e89d` when absent |
| `FUNCTIONS_EMULATOR` | Firebase emulator (`true`) | Marks the process as local; the integrations card (`GET /v1/admin/integrations`) reports the Firebase entry as `emulator` |
| `FUNCTIONS_CONTROL_API` | Firebase CLI during deploy analysis (`true`) | Params return their defaults instead of calling `.value()`, avoiding the "invoked during function deployment" warning |
| `NODE_ENV` | Node / vitest (`test`) | `test` silences the logger; anything else is treated as production |
| `LOG_LEVEL` | shell (optional) | pino level override (`debug`, `info`, `warn`, `error`); default `info`, `silent` under tests |

`.env.example` mirrors the params and secrets above for local setup.

## WhatsApp via Twilio

Customer WhatsApp messages go out through the Twilio Messaging Service that the legacy admin used (`MG4d8b6037dc3b183f43b2622307271660`) with its approved **Content templates** (`quote_ready` → `HX011c…`, `service_ready` / `pickup_otp` → `HX63a7…`; bindings live in `notification_templates.provider_template_sid` / `provider_variables`, migration `0004`). Adapter: `src/lib/whatsapp.ts` (`TwilioWhatsAppAdapter`, plain `fetch` against `/2010-04-01/Accounts/{sid}/Messages.json`, one retry on 5xx/network, Twilio error codes mapped to `notifications.provider_error_code`).

1. **Secrets** — `firebase functions:secrets:set TWILIO_ACCOUNT_SID` and `firebase functions:secrets:set TWILIO_AUTH_TOKEN` (emulator: `.secret.local`).
2. **Params** in `backend/functions/.env`:
   ```
   WHATSAPP_PROVIDER=twilio                                   # or sandbox (logs only); defaults to twilio when the secrets are set
   TWILIO_MESSAGING_SERVICE_SID=MG4d8b6037dc3b183f43b2622307271660
   TWILIO_WHATSAPP_FROM=                                      # optional whatsapp:+27… sender, only used without a Messaging Service
   PUBLIC_API_BASE_URL=https://europe-west1-sparkling-4e89d.cloudfunctions.net/api
   ```
3. **Status callback** — with `PUBLIC_API_BASE_URL` set, every send passes `StatusCallback=<base>/v1/notifications/twilio/status`; also paste that URL into the Messaging Service → *Integration* → *Delivery status callback* in the Twilio console so receipts arrive for every message. The route is public but validates `X-Twilio-Signature` (HMAC-SHA1 of the URL + sorted params with the auth token) and updates `notifications` by `provider_ref = MessageSid` (`sent` → `delivered` → `read`; `failed`/`undelivered` with the error code).
4. **Feature flag** — `whatsapp_enabled` stays **off** (seed default) until the WhatsApp sender is verified on the Messaging Service; while off, WhatsApp rows are stored as `suppressed` and can be re-sent later. Flip it with `PATCH /v1/admin/flags/whatsapp_enabled {"enabled":true}`.
5. **Check** — `GET /v1/admin/integrations` → `whatsapp {provider, configured, messaging_service, status_callback, enabled}`.
6. **Smoke test** (deployed): pick a `failed`/`suppressed` WhatsApp row from `GET /v1/admin/notifications?channel=whatsapp&status=failed,suppressed` and re-send it — the recipient must be an opted-in test number:
   ```bash
   API=https://europe-west1-sparkling-4e89d.cloudfunctions.net/api/v1
   TOKEN=$(...)   # Firebase ID token of a manager/admin
   curl -s "$API/admin/notifications?channel=whatsapp&limit=5" -H "Authorization: Bearer $TOKEN" | jq '.data[] | {id, status, provider_error_code, error}'
   curl -s -X POST "$API/admin/notifications/<id>/resend" -H "Authorization: Bearer $TOKEN" | jq '.outcome, .notification.provider_ref'
   ```
   Then watch the row move to `delivered` via the callback (`provider_status`, `delivered_at`).

Free-form (non-template) bodies are only delivered inside a 24-hour customer session (Twilio 63016 otherwise) — every customer-facing template is therefore bound to a Content SID. Phone numbers are normalised to E.164 (`082 123 4567` → `+27821234567`); invalid numbers fail locally with code `21211`.

## Supabase: Third-Party Auth for Firebase (one-time)

Clients read through RLS and subscribe to Realtime with their **Firebase** ID token. Enable it once per Supabase project:

1. Supabase dashboard → **Authentication → Sign In / Providers → Third-Party Auth** → **Add provider → Firebase**.
2. Enter the Firebase project id `sparkling-4e89d` and save.
3. Clients create the Supabase client with `accessToken: () => firebaseUser.getIdToken()`.
4. RLS helpers `app.role()` / `app.outlet_ids()` (migration 0001 §2) read the custom claims that `POST /v1/auth/session` mints.

Alternatively with the CLI: `supabase config push` after adding
```toml
[auth.third_party.firebase]
enabled = true
project_id = "sparkling-4e89d"
```

## Behaviour notes

* **Auth** — `POST /auth/session` upserts the profile; a seeded profile with the same e-mail (`seed_*` id) is claimed by rewriting its `id` to the Firebase UID (FKs cascade). Custom claims `role` + `outlet_ids` are (re)set only when they differ; the response says `claims_updated`.
* **Idempotency** — `Idempotency-Key` header or `client_op_id` body field, scoped by `uid + method + path`, cached in `idempotency_keys`. Domain tables with `client_op_id` (bookings, quotations, tasks, step results, movements, task_events, sync_operations) are additionally deduped by their unique columns.
* **Pricing / points** — effective price = outlet override ?? base; discount from the *published* loyalty config tier. `points_pending = round(total_rand × points_per_rand)` (R198 × 0.10 → 20, matching the API.md reference payload); the tier `earn_multiplier` is applied when the earn ledger row is posted on verification (`round(20 × 1.25) = 25`), idempotency key `booking:<id>:earn`.
* **Payments** — `PaymentProvider { createIntent, verifyWebhook, parseEvent }`; the shipped `SandboxProvider` signs with HMAC-SHA256 (`X-Signature`). Webhooks insert `payment_events` first; a duplicate `(provider, provider_event_id)` returns `{duplicate:true}` with no side effects. Receipt numbers `RCP-<n>` come from `receipt_ref_seq` (70000+) via the service-role RPC `next_receipt_no()` (migration 0002); if the RPC errors the API falls back to `max+1` and retries on the unique constraint.
* **Task verification** — `verified` (supervisor/manager only) marks the booking `completed`, posts loyalty + staff points (published `gamification_rules`), issues a 5-digit **collection OTP** (`work_orders.pickup_otp`, crypto-random), sends `service_ready` (push + WhatsApp, OTP included), and audits. The OTP is exposed only to the owning customer (`GET /bookings/:id` while `completed` and uncollected); staff confirm it with `POST /work-orders/:id/pickup/verify` (5 attempts, then locked) or re-send it with `POST /work-orders/:id/pickup/resend` (1/min). `completed`/`verified` require all `required` steps `done` unless a supervisor passes `override.reason` (recorded as a `task_events` row `event='override'`).
* **Sync** — `POST /sync/batch` applies ops in order; each is stored in `sync_operations`; replays return the stored result; state clashes come back as `conflict` with `server_state`.
* **Rate limits** — in-memory token buckets per uid/ip on auth, booking and payment routes (per instance).
