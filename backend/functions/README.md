# Sparkling API — Firebase Cloud Functions (`backend/functions`)

Single Express app exported as the 2nd-gen HTTPS function **`api`** (region `europe-west1`), mounted at `/v1`.
Implements [`docs/API.md`](../../docs/API.md) on top of the Supabase schema in [`backend/supabase`](../supabase).

```
Node 22 · TypeScript · express · firebase-functions v6 · firebase-admin · @supabase/supabase-js v2 · zod · pino · csv-stringify · busboy · pdfkit · qrcode · image-size · vitest
```

| `tests/` | vitest suites with an in-memory Supabase stub (`tests/helpers/fakeSupabase.ts`) and storage fake (`tests/helpers/fakeStorage.ts`) — no network |

## Environment variables

Every variable the API reads, where it comes from and what happens when it is missing. Params and secrets are declared in `src/config.ts` with `firebase-functions/params`; a plain `process.env` value of the same name always wins (that is how the emulator, tests and `.env` files feed them). Values are read at request time, never at import, so the deploy-time code analysis never touches Secret Manager.

### Secrets — Cloud Secret Manager, set once per project, never in the repo (INT-006, SEC-005)

| Name | Required | Used for | Where to get it |
|---|---|---|---|
| `SUPABASE_SERVICE_ROLE_KEY` | yes | Service-role Supabase client for every database read/write (bypasses RLS; server only) | Supabase → Project Settings → API Keys → *secret* (`sb_secret_…`) or legacy `service_role` JWT |
| `PAYMENT_WEBHOOK_SECRET` | yes | HMAC key that signs/validates payment-provider webhooks (`POST /v1/payments/webhook`, sandbox confirm) | Any long random string, e.g. `openssl rand -hex 32`; a real provider gives you its signing secret |
| `TWILIO_ACCOUNT_SID` | for WhatsApp | Basic-auth user for the Twilio REST API; also used to validate `X-Twilio-Signature` | Twilio Console → Account Info (`AC…`, 34 chars) |
| `TWILIO_AUTH_TOKEN` | for WhatsApp | Basic-auth password for Twilio; HMAC key for status-callback signature validation | Twilio Console → Account Info → Auth Token |

```bash
firebase functions:secrets:set SUPABASE_SERVICE_ROLE_KEY --project sparkling-4e89d
openssl rand -hex 32 | firebase functions:secrets:set PAYMENT_WEBHOOK_SECRET --project sparkling-4e89d --data-file=-
firebase functions:secrets:set TWILIO_ACCOUNT_SID --project sparkling-4e89d
firebase functions:secrets:set TWILIO_AUTH_TOKEN  --project sparkling-4e89d
```
Secret Manager rejects empty values, and `firebase deploy` prompts for any secret that has no version yet — set them all **before** the first deploy. Missing Twilio secrets are not fatal: WhatsApp silently falls back to the sandbox adapter (see `WHATSAPP_PROVIDER`). For the emulator put the same names in `backend/functions/.secret.local` (git-ignored).

## WhatsApp via Twilio

Customer WhatsApp messages go out through the Twilio Messaging Service that the legacy admin used (`MG4d8b6037dc3b183f43b2622307271660`) with its approved **Content templates** (`quote_ready` → `HX011c…`, `service_ready` / `pickup_otp` → `HX63a7…`; bindings live in `notification_templates.provider_template_sid` / `provider_variables`, migration `0004`). Adapter: `src/lib/whatsapp.ts` (`TwilioWhatsAppAdapter`, plain `fetch` against `/2010-04-01/Accounts/{sid}/Messages.json`, one retry on 5xx/network, Twilio error codes mapped to `notifications.provider_error_code`).

1. **Secrets** — `firebase functions:secrets:set TWILIO_ACCOUNT_SID` and `firebase functions:secrets:set TWILIO_AUTH_TOKEN` (emulator: `.secret.local`).
2. **Params** in `backend/functions/.env`:
   ```
   WHATSAPP_PROVIDER=twilio                                   # or sandbox (logs only); defaults to twilio when the secrets are set
   TWILIO_MESSAGING_SERVICE_SID=MG4d8b6037dc3b183f43b2622307271660
   TWILIO_WHATSAPP_FROM=                                      # optional whatsapp:+27… sender, only used without a Messaging Service
   PUBLIC_API_BASE_URL=https://europe-west1-sparkling-4e89d.cloudfunctions.net/api
   ```
3. **Status callback** — with `PUBLIC_API_BASE_URL` set, every send passes `StatusCallback=<base>/v1/notifications/twilio/status`; also paste that URL into the Messaging Service → *Integration* → *Delivery status callback* in the Twilio console so receipts arrive for every message. The route is public but validates `X-Twilio-Signature` (HMAC-SHA1 of the URL + sorted params with the auth token) and updates `notifications` by `provider_ref = MessageSid` (`sent` → `delivered` → `read`; `failed`/`undelivered` with the error code).
4. **Feature flag** — `whatsapp_enabled` stays **off** (seed default) until the WhatsApp sender is verified on the Messaging Service; while off, WhatsApp rows are stored as `suppressed` and can be re-sent later. Flip it with `PATCH /v1/admin/flags/whatsapp_enabled {"enabled":true}`.
5. **Check** — `GET /v1/admin/integrations` → `whatsapp {provider, configured, messaging_service, status_callback, enabled}`.
6. **Smoke test** (deployed): pick a `failed`/`suppressed` WhatsApp row from `GET /v1/admin/notifications?channel=whatsapp&status=failed,suppressed` and re-send it — the recipient must be an opted-in test number:
   ```bash
   API=https://europe-west1-sparkling-4e89d.cloudfunctions.net/api/v1
   TOKEN=$(...)   # Firebase ID token of a manager/admin
   curl -s "$API/admin/notifications?channel=whatsapp&limit=5" -H "Authorization: Bearer $TOKEN" | jq '.data[] | {id, status, provider_error_code, error}'
   curl -s -X POST "$API/admin/notifications/<id>/resend" -H "Authorization: Bearer $TOKEN" | jq '.outcome, .notification.provider_ref'
   ```
   Then watch the row move to `delivered` via the callback (`provider_status`, `delivered_at`).

Free-form (non-template) bodies are only delivered inside a 24-hour customer session (Twilio 63016 otherwise) — every customer-facing template is therefore bound to a Content SID. Phone numbers are normalised to E.164 (`082 123 4567` → `+27821234567`); invalid numbers fail locally with code `21211`.

## Public quotation page (CUS-030..034, STF-010/012)

Staff raise a quote for a walk-in customer in one step (`POST /v1/quotations` with `customer_id`, `items[]`, `valid_until`); the row starts `quoted` with a fresh `public_token` (30 days) and the customer receives `quote_ready` (push + WhatsApp). The public page — hosted by the admin app at `PUBLIC_WEB_BASE_URL/q/<token>` — talks to the **unauthenticated, token-scoped** API under `/v1/public/quotations/:token` (mounted before the auth middleware, CORS open for GET/POST, 60 req/min per IP + token):

| Method | Path | Notes |
|---|---|---|
| GET | `/public/quotations/:token` | `{ ref, status, outlet{name,phone,address_line}, customer{first_name}, vehicle, items, amount_cents, currency, valid_until, quoted_at, decided_at, decision_source, expired, can_decide, attachments[{id,url,caption,width,height}], pdf_url, notes }` — no phone / e-mail / ids. 404 unknown token; 410 `gone` `{ref,status}` once the link expired |
| GET | `/public/quotations/:token/photos/:attachmentId` | streams the damage photo (`Cache-Control: private, max-age=3600`) |
| GET | `/public/quotations/:token/pdf` | same A4 PDF as `GET /quotations/:id/pdf` |
| POST | `/public/quotations/:token/decision` | `{ decision: accept\|decline, note?, accepted_by_name? }` → `decision_source:'public_link'`, `decision_by_name`; audited `quotation.decision_public` with IP + user agent; `quote_decided` push to the assessor + outlet supervisors/managers, `quote_decision_receipt` (push + WhatsApp) to the customer; returns the public view |

Signed-in counterparts on `/v1/quotations/:id`: `POST …/photos` (multipart `photo` + `caption`, jpeg/png/heic/webp sniffed by magic bytes, ≤ 10 MB, ≤ 10 per quotation, owner or outlet staff, refused after the decision), `GET`/`DELETE …/photos/:attachmentId` (delete: staff, pre-decision), `POST …/share` (staff; rotates the token + 30 days, re-sends `quote_ready`, 1/min per quotation, audited `quotation.share`), `GET …/pdf` (owner / staff; `Content-Disposition: attachment; filename="<ref>.pdf"`, stamps `pdf_generated_at` on first render). `GET /quotations/:id` (and the list) now carries `items` (alias of `line_items`), `attachments[]` with API `url`s, `decision_source`, `decision_by_name`, `pdf_url`, and — staff only — `public_url`. The raw `public_token` is never listed.

**Decisions are one-time.** The first accept/decline — in the app (`POST /quotations/:id/decision`, `decision_source:'app'`) or via the link — wins; every later call answers 409 `conflict` `{ decided_at, status }`. Only `quoted` quotations can be decided (409 `invalid_transition` otherwise); accepting after `valid_until` marks the row `expired` and answers 410 `gone`.

Setup:
1. `PUBLIC_WEB_BASE_URL=https://<admin-app-origin>` in `backend/functions/.env` (the admin app serves `/q/<token>`).
2. Apply migration `0006_quotation_public.sql` (columns, index, template rows).
3. **Twilio Content template `quote_ready`** (`HX011c…`): the button URL must be `<PUBLIC_WEB_BASE_URL>/q/{{2}}` — variable `1` = `first_name`, variable `2` = `public_token` (`provider_variables` is rebound by migration 0006). Re-submit the template for approval after changing the URL.
4. Photos need the default Cloud Storage bucket (`sparkling-4e89d.firebasestorage.app`); the function's service account already has object admin. Objects are private — they are only ever streamed through the API.

## Behaviour notes

* **Auth** — `POST /auth/session` upserts the profile; a seeded (`seed_*`) or walk-in (`walkin_*`) profile with the same e-mail — or, for walk-ins, the same phone (Firebase `phone_number` claim → user record → body `phone`, normalised to E.164) — is claimed by rewriting its `id` to the Firebase UID (FKs cascade: bookings, vehicles and points carry over). Custom claims `role` + `outlet_ids` are (re)set only when they differ; the response says `claims_updated`.
* **Walk-ins (STF-010/012)** — `GET /staff/customers?search` matches name / e-mail / phone in any formatting (`083…` finds `+2783…`) / plate (alphanumerics only), max 25 rows, audited once as `customer.search`. `POST /staff/customers` registers a `walkin_<uuid>` profile + silver loyalty account (409 `conflict` with `existing_customer` on a known phone/e-mail; idempotent by `client_op_id`; audited `customer.create`). `POST /staff/customers/:id/vehicles` reuses the vehicle service (duplicate → 409 `existing_vehicle_id`, `force` merges; scans are `disc_verified` only with a `disc_hash`). `POST /bookings` with `walk_in:true` (staff, `customer_id` required, outlet in scope) defaults `slot_start` to *now rounded up to the outlet's `slot_minutes` grid* (strictly after now, capacity enforced by `get_available_slots` → 409 when all bays are busy or the outlet is closed), starts `confirmed`, records `created_by` + `walk_in`, audits `booking.create_walk_in`; `checkin:{bay?,priority?}` runs the check-in flow and returns `work_order` + `task`.
* **POS payments** — `POST /payments/record` (staff, booking's outlet) attests a cash / card-terminal payment: amount must equal `total_cents` (400), an already-paid booking is refused (409 with the payment) unless the same `idempotency_key` replays; writes `payments` (`provider:'pos'`, `method`, `recorded_by`, `successful`, `verified_at`, receipt from `next_receipt_no()`), a `payment_events` row `pos.recorded` (`provider_event_id` = `<uid>:<idempotency_key>`), confirms a pending booking, sends `payment_successful` and audits `payment.record`. Migration `0005_walk_in.sql` adds `payments.method/recorded_by`, `bookings.walk_in/created_by_staff` and a `profiles(phone)` index.
* **Quotations** — customers request (`requested`); supervisors quote (`POST /quotations/:id/quote`, now also issues a public token) or staff raise a quote directly (see *Public quotation page*). Damage photos live in Cloud Storage under `quotations/<quotation_id>/`, typed by magic bytes (never by the client's `Content-Type`), with header-only dimension parsing (`image-size`). Migration `0006_quotation_public.sql` adds `quotations.public_token/public_token_expires_at/decision_source/decision_by_name/items_note/pdf_generated_at`, `attachments.kind/width/height/caption`, and the `quote_decided` / `quote_decision_receipt` templates.
* **Idempotency** — `Idempotency-Key` header or `client_op_id` body field, scoped by `uid + method + path`, cached in `idempotency_keys`. Domain tables with `client_op_id` (bookings, quotations, tasks, step results, movements, task_events, sync_operations) are additionally deduped by their unique columns.
* **Catalogue pricing (migration 0008, `docs/CATALOGUE.md`)** — `services` are the canonical rows (`code`, `group_name`, `pricing_mode` `from|fixed|by_quote`, `vat_mode` `incl|excl`, optional default prices, `is_addon` + `addon_group_name`); each outlet binds one in `outlet_services` with its own `display_name`, `price_small/large/general_cents`, mode/VAT overrides (null = inherit), `sort_order`, `notes`, `is_available`. Composition lives in `service_components` (`outlet_id` null = global default; any outlet rows for a parent replace the global set at that outlet). `GET /outlets/:id/services` returns `{ data: [offer], groups }` with `price_for.{small,large,bike}`, `price_from_cents`, `price_label`, `includes` / `included_in`; `?vehicle_size` adds `price_cents`/`total_cents` for that size. Vehicle size = `vehicles.size_class` ?? licence-disc description (hatch/sedan/coupé → small; station wagon/SUV/pick-up/bakkie/bus/MPV/van → large; motorcycle → bike) ?? small; `POST /vehicles` derives it from `description` when `size_class` is omitted. Admin: `GET/POST/PUT /admin/services` (+ `components` = global set; `by_quote` needs no prices, `from`/`fixed` need at least one, add-ons need `addon_group_name`, self/cyclic composition → 400 — a non-pricing edit of a legacy service without default prices is still allowed), `GET /admin/outlets/:id/services` (offers incl. unavailable, `components_source`), `PUT /admin/outlets/:id/services/:serviceId` (documented fields + `components` array → outlet set, `null` → back to global; the effective card must be priceable unless by-quote), `DELETE` drops the binding and its outlet composition rows. Audited `service.create/update`, `outlet_service.update/delete`.
* **Pricing / points** — `base_cents` = outlet price for the booking's `vehicle_size` (small/large; `general` when size-independent; bike prices as small) ?? service default; `by_quote` services are refused with 409 `validation_error` `{ reason: 'by_quote' }` (request a quotation instead); `from` prices are minimums and labelled "From R x". `addon_service_ids[]` must be available `is_addon` offers whose `addon_group_name` equals the service's `group_name` (400 otherwise) and are priced the same way into `addons_cents`; `price_cents = base + addons`; the tier discount (from the *published* loyalty config) applies to that sum; `vat_mode: excl` adds 15% VAT on the discounted amount (`vat_cents`), `incl` prices are final; `total_cents = price − discount + vat`. Bookings store `vehicle_size`, `pricing_mode`, `vat_mode`, `addon_service_ids`, `addons_cents`; reads add `addons[]` (name + price) and `price_label`; the bookings CSV gains `vehicle_size`, `addons`, `vat_mode`. `points_pending = round(total_rand × points_per_rand)` (R198 × 0.10 → 20, matching the API.md reference payload); the tier `earn_multiplier` is applied when the earn ledger row is posted on verification (`round(20 × 1.25) = 25`), idempotency key `booking:<id>:earn`.
* **Payments** — `PaymentProvider { createIntent, verifyWebhook, parseEvent }`; the shipped `SandboxProvider` signs with HMAC-SHA256 (`X-Signature`). Webhooks insert `payment_events` first; a duplicate `(provider, provider_event_id)` returns `{duplicate:true}` with no side effects. Receipt numbers `RCP-<n>` come from `receipt_ref_seq` (70000+) via the service-role RPC `next_receipt_no()` (migration 0002); if the RPC errors the API falls back to `max+1` and retries on the unique constraint.
* **Task verification** — `verified` (supervisor/manager only) marks the booking `completed`, posts loyalty + staff points (published `gamification_rules`), issues a 5-digit **collection OTP** (`work_orders.pickup_otp`, crypto-random), sends `service_ready` (push + WhatsApp, OTP included), and audits. The OTP is exposed only to the owning customer (`GET /bookings/:id` while `completed` and uncollected); staff confirm it with `POST /work-orders/:id/pickup/verify` (5 attempts, then locked) or re-send it with `POST /work-orders/:id/pickup/resend` (1/min). `completed`/`verified` require all `required` steps `done` unless a supervisor passes `override.reason` (recorded as a `task_events` row `event='override'`).
* **Sync** — `POST /sync/batch` applies ops in order; each is stored in `sync_operations`; replays return the stored result; state clashes come back as `conflict` with `server_state`.
* **Rate limits** — in-memory token buckets per uid/ip on auth, booking and payment routes, per IP + token on `/public/quotations` (per instance); `POST /quotations/:id/share` is additionally limited to one `quote_ready` per quotation per minute via the `notifications` table (works across instances).
