# South African licence disc PDF417 — confirmed layout and scan findings

SRS §15 (BAR-001…010, INT-005) required the disc schema to be confirmed against real samples before production acceptance. On 9 Sep 2026 five photographs of real discs (`~/Desktop/Sparkling/Car Disc Samples`) were decoded offline with zxing-cpp (`tools/pdf417/decode_discs.py`).

## Confirmed payload layout

The barcode text is `%`-delimited. Positional fields (0-based after `split('%')`), verified on a decoded Renault Kwid disc:

| Index | Content | Example |
|---|---|---|
| 1 | Control / version | `MVL1CC73` |
| 2 | Form id | `0146` |
| 3 | Disc serial | `4025M007` |
| 4 | Flag | `1` |
| 5 | Licence disc number (printed as "NO.") | `4025013HM0M8` |
| 6 | Licence number = registration plate | `KK10FCGP` |
| 7 | Vehicle register number | `DJJ697X` |
| 8 | Description (EN / AF) | `Hatch back / Luikrug` |
| 9 | Make | `RENAULT` |
| 10 | Model | `KWID` |
| 11 | Colour (EN / AF) | `White / Wit` |
| 12 | VIN | `MEEBBA00900798734` |
| 13 | Engine number | `B4DA404E217984` |
| 14 | Expiry date | `2026-06-30` |

This matches the layout assumed in `packages/sparkling_core/lib/src/scanning/pdf417_disc_parser.dart` and `backend/functions/src/lib/pdf417.ts`. Both parsers now carry the real payload as a test fixture (`test/pdf417_real_disc_test.dart`, `tests/pdf417_real.test.ts`). Fees, GVM, tare, test date and seating shown on the printed disc are **not** in the barcode.

## Decode results from the five photos

Two decoders were tried. The offline experiment (zxing-cpp, `tools/pdf417/decode_discs.py`) is a weak proxy; the authoritative result is the apps' own decoder (`mobile_scanner` → Google ML Kit on Android, Apple Vision on iOS) exercised by `apps/customer/integration_test/disc_photo_decode_test.dart` with the photos embedded as fixtures. Full raw payloads and parsed fields: `apps/customer/integration_test/RESULTS.md`.

| Photo | Vehicle | zxing-cpp (offline) | ML Kit in-app (Pixel 10 emulator) |
|---|---|---|---|
| disc_1 (5) | Mahindra XUV300, LHP858NW | corrupt symbol passed checksum → parser rejected it (CUS-012/BAR-006 path) | decoded + parsed |
| disc_2 (6) | Renault Kwid, KK10FCGP | decoded (2× upscale) | decoded + parsed |
| disc_3 (7) | Ford Territory, LJL416NW | not decoded | decoded + parsed |
| disc_4 (8) | Ford Ranger, KMM808NW | not decoded | decoded + parsed |
| disc_5 (9) | Toyota Urban Cruiser, KXR596NW | not decoded | decoded + parsed |

ML Kit decoded all five WhatsApp-compressed 960×1280 photos with no pre-processing, and every payload parsed to the correct registration, VIN, engine number, make, model, colour and expiry (VINs validated; expired discs flagged). The zxing failures were resolution-bound (under 2 px per module against the ~3 px/module that decoder needs), so the earlier resolution concern applies to third-party decoders, not to the shipped scanner.

Apple Vision could not be exercised: `mobile_scanner` refuses `analyzeImage` on the iOS *simulator* (unsupported-operation error), so iOS photo import needs a physical iPhone to verify. Live camera scanning on iOS is unaffected.

## Consequences for the apps

- Live camera scanning (`mobile_scanner`, PDF417 only) uses `cameraResolution` 1920×1080 on Android, a `scanWindow` matching the viewfinder, autofocus and the `ScanDebouncer` (BAR-010).
- "Import photo" (gallery) runs the same ML Kit / Vision decoder through `analyzeImage`; on failure the BAR-006 sheet offers Retry or manual entry.
- Both parsers reject corrupt payloads and never populate a vehicle from unvalidated text (BAR-005).
